# 输入桥迭代需求：BOTW 动作宏与可靠输入

日期：2026-11-02。版本：v0.1。本文定义拟实现的产品行为与验收要求；动作宏、采样确认与客户端动作键均尚未实现。任务状态以 [backlog](../tasks/backlog.json) 为准。

## 1. 目标与使用场景

让 Pad 玩家通过一个动作键完成 BOTW 的常用组合操作，同时保留普通触屏、手柄和镜头控制。首版由玩家判断敌人出手时机，NXBridge 负责可靠地执行动作序列。

- 玩家点“后翻”，主机执行锁定、后方向和跳跃的组合；无需同时操作多个触控区域。
- 玩家自行掌握招架时机，点“招架”后执行举盾和招架输入；不承诺完美盾反成功。
- 玩家操作中可以取消动作或立即接管；动作结束不释放玩家自己仍按着的盾键。
- 每个玩家的动作只进入自己的 BOTW 进程。断线、换控制设备或重启游戏后，旧动作不得继续。

本需求是原生串流路线上的可选输入增强，不改变 [服务端设计](game-session-server.md) 的媒体路线，也不成为 Rust 合成音画、离屏输出或基础串流的前置依赖。

## 2. 当前依据与缺口

| 已有依据 | 可以确认 | 仍需补齐 |
| --- | --- | --- |
| [NXB-045](reports/NXB-045.md)、[NXB-047](reports/NXB-047.md) | 单会话按键、双摇杆、组合输入已到达游戏采样；后者使用原生 GameStream 手柄通道 | 正式 Rust 输入链路、多会话、动作调度和手感验收 |
| [输入接收器](../adapters/input/nxbridge_input.c) | `held / latch` 保留短按，摇杆保存最新值 | 单个锁存位不能完整表达同键多次按下 / 释放；摇杆提前归零可能破坏组合输入 |
| [输入接口草案](input-bridge.md) | 已提出会话归属、顺序、断线中和和采样时间记录 | 可执行的宏状态机、输入来源仲裁、采样确认与客户端触发约定 |

NXB-047 的一次受控断线中和约为 2.1 秒，使用临时连接超时；这不是本需求的延迟成绩。离屏帧与 PCM 不自动提供敌人攻击状态、完美防御判定窗口或游戏菜单状态。

## 3. 首版范围与后续能力

### 首版五个动作键

下表按 BOTW 默认键位描述动作意图。落地时须对固定游戏版本、实际键位与运行时轴方向逐一校准；表内没有已验证的等待时长。

| 动作 ID / 标签 | 候选输入序列 | 前置条件与成功口径 |
| --- | --- | --- |
| `backflip` / 后翻 | 保持 ZL，建立后方向，再产生 X 的按下与释放 | 地面且角色可行动；实际出现后翻动画；不要求触发完美闪避 |
| `sidestep_left` / 左侧跳 | 保持 ZL，建立左方向，再产生 X 的按下与释放 | 地面且角色可行动；实际向目标侧跳 |
| `sidestep_right` / 右侧跳 | 保持 ZL，建立右方向，再产生 X 的按下与释放 | 同上，方向独立验证 |
| `parry` / 招架 | 保持 ZL，按配置建立举盾阶段，再短按 A | 装备可用盾且能举盾；实际出现招架动作；反击是否成功另计 |
| `shield_surf` / 滑盾 | 保持 ZL，短按 X，按校准间隔在空中短按 A | 装备可用盾、具备起跳空间；实际进入滑盾动作 |

- 五个动作均为一次触发、一次有限序列。首版不长按循环、不自动连发、不排队执行第二个动作。
- 跳跃键交换等游戏设置必须体现在配置中。未知配置不能标记为已适配。
- 已在举盾与尚未举盾的招架路径可能需要不同准备时长，必须记录条件；不假设两者延迟相同。
- 战斗中断、装备不满足、菜单、地形或角色硬直都可能阻止动作。首版没有状态识别时，由玩家满足前置条件；不能凭输入日志宣称游戏动作成功。

### 后续候选

连击、蓄力、连续拾取、录制 / 回放和菜单操作单列后续需求。自动完美盾反、自动完美闪避、自动林克时间需要额外的画面识别或游戏状态适配；本轮不定义其成功率，也不以固定延时宏冒充这些能力。体感与震动继续按原有独立任务验收。

## 4. 玩家体验与触发方式

| 编号 | 要求 |
| --- | --- |
| UX-01 | BOTW 档案可显式开启五个动作键；普通按键与手柄模式仍可使用。首次使用提供简短前置条件说明。 |
| UX-02 | 点按产生一次触发，长按不重复触发；宏运行时再次点按返回“动作执行中”，不积累操作。必须提供明确的取消入口。 |
| UX-03 | 显示可用、执行中、已取消、连接不可用等状态。“执行结束”只表示输入序列结束，不显示未经观测的“盾反成功”。 |
| UX-04 | 断线、重新配对、控制权转移、配置变化或游戏重启后回到未执行状态；玩家重新触发才开始。 |
| UX-05 | 人工镜头操作在不冲突时继续生效。冲突的移动或按键操作优先接管，取消当前宏。 |

网络输入继续使用已认证的 GameStream 会话，不新增独立局域网输入服务。专用动作键需要客户端适配；原版 Moonlight 不应被描述为已有宏命令接口。

首版应以客户端与主机共同配置、经过实测的既有输入事件绑定承载触发。实现前固定所用事件、去重与取消语义；被选作专用触发的事件必须被主机消费，不能同时泄漏成游戏里的普通按键。不得猜测协议存在未使用的标志位。若需要自定义消息扩展，须先补充版本 / 能力协商设计；不支持宏的客户端保留普通输入并隐藏动作键。

接受、忙、执行结束等状态须来自主机确认。反馈能力未协商时只能显示“已发送 / 状态未知”，不能从触摸结束或本地计时推断主机执行结果。回执承载与触发绑定一并在实现前确定，不假设 GameStream 已有宏状态字段。

## 5. 执行、时序与输入仲裁

### 主机执行与有限配置

Pad 发送触发，主机在绑定的游戏输入路径附近执行完整序列。这样宏内部各步骤不依赖逐次经过 Wi-Fi；首次触发与画面反馈仍承担串流延迟。执行器放入每会话输入路径，生命周期由 Host 管理；不将宏逻辑塞进媒体 ABI。

配置采用有限的声明式动作列表：动作 ID、配置版本、键位映射、需要占用的按键 / 轴、按下 / 释放步骤、保持条件、取消条件和总时限。首版只启用通过动作验收的五个预置动作，不执行客户端传来的任意脚本或命令。具体文件格式与模块拆分留给实现任务确定。

首版预算：每会话最多一个活动宏、零个待执行宏；每个宏最多 32 个步骤、总时限最多 2 秒。以上是待验证的工程上限，不是动作的实际耗时。改变上限须记录原因和配置版本。

### 输入状态与采样

| 编号 | 要求 |
| --- | --- |
| IN-01 | 一个步骤中的按键与摇杆作为一致的组合状态发布；后翻的方向不能在 X 被采样前归零。普通连续摇杆仍采用最新状态，不为旧摇杆位置建立无界队列。 |
| IN-02 | 宏按下、保持、释放必须保序，必要阶段保持到有效采样确认；同键两次短按之间的释放必须被采样，不能合并成一次长按或一个锁存位。 |
| IN-03 | 同时记录输入发布、运行时取样和游戏动作证据。一次 `nxbridge_input_sample` 调用不自动等于一次游戏逻辑更新；实现必须说明有效采样周期的定义。 |
| IN-04 | 有可用游戏更新时钟时按其调度；否则采用经校准的单调时钟节奏加采样确认，并标记其精度限制。不按 60 FPS 视频包数或固定 `sleep` 循环宣称游戏帧精确。 |
| IN-05 | 游戏采样停顿超过初始目标 250 ms、步骤超时或总时限到期时取消宏。恢复后不集中补发过期步骤；看门狗不依赖停止推进的游戏时钟。 |
| IN-06 | 执行器不得在渲染 / 输入采样线程中等待网络或阻塞计时。宏关闭时，人工直通路径不因宏功能增加固定的一帧等待。 |

各动作的保持周期、阶段间隔和有效采样定义均需要实测后写入版本化配置。不得把“30 FPS 约 33.3 ms”直接当成招架窗口或所有动作的正确按键时长。

### 人工与宏输入的归属

- 分别维护人工输入和宏拥有的输入状态，再生成唯一的游戏输入快照；不能仅把双方位图 OR 后统一清零，也不能按摇杆幅度大小决定控制权。
- 正常结束或取消只移除宏贡献，按**最新有效人工状态**重新合成。玩家仍按住 ZL 时，宏结束不能替玩家松盾；玩家已经松手时，也不能恢复开始前的旧 ZL 状态。
- 首版启动前，宏独占的摇杆须在配置死区内，需要产生新按下边沿的按钮须已释放；否则拒绝启动并提示松开相应控制。已有 ZL 保持可作为共享条件。
- 运行中，人工改变宏占用的按键或将占用轴推离死区时，取消宏并交回人工状态；不相关右摇杆镜头输入继续直通。死区以配置记录，不把每次重复的手柄状态包当成新的接管意图。
- 来自人工输入的取消键、B、菜单 / 系统界面相关按键，以及控制权撤销，优先于宏下一步；先清除宏贡献，再交付应保留的人工事件。宏生成的按键不反过来触发自身取消。已有宏步骤尚未被采样时也不得越过取消指令继续执行。
- 断线、会话终止或代次变化时，人工与宏输入一起中和；重连不恢复旧按住状态和未完成动作。

## 6. 会话、去重与失败处理

每个活动动作绑定 `session_id`、游戏运行代次、控制权代次、宏配置版本和触发序号。连接建立时确定归属，不接受客户端任意选择本机进程。内部动作标识不表示 GameStream 已有对应网络字段。

| 情况 | 必须行为 |
| --- | --- |
| 触发键持续保持 / 重复包 | 同一次按下只执行一次；必须看到有效释放后才能再次触发 |
| 宏执行期间收到另一触发 | 拒绝并报告忙；不隐式排队，不以第二次触发重新计时 |
| 重复、过期或旧代次触发 | 丢弃并记录原因，不影响当前玩家的人工控制 |
| 源队列溢出或控制通道错误 | 停止该来源，清除其待执行输入并中和；不得悄悄丢弃释放后继续运行 |
| 客户端失联 | 取消宏、丢弃待处理步骤并中和；宏自身不能刷新客户端存活计时 |
| 游戏源退出、重启或输入源切换 | 原运行代次失效，清空状态；新代次等待新的有效人工输入与触发 |
| 用户打开菜单 | 对已观测到的菜单输入先取消宏；没有状态识别时不宣称能检测所有游戏内菜单或暂停情况 |
| 暂停、长卡顿后恢复 | 不追赶旧步骤，不延迟执行旧招架；重新触发才允许新宏 |

沿用输入桥的静默失联目标：自最后一次有效客户端存活证据起 250 ms 内，主机取消动作并将合成状态置为中和；游戏应在下一次有效采样看到释放。显式断开应立即处理。客户端心跳周期与误超时率必须实测，现有约 2.1 秒实验结果不满足该目标。游戏停顿期间分别报告主机中和时间与游戏实际采样时间。

## 7. 可观察性与性能口径

每次执行记录会话 / 代次、宏与配置版本、触发接收、接受 / 拒绝原因、步骤发布与采样、结束 / 取消原因，以及队列峰值。诊断日志使用有界缓冲，不在热路径逐帧同步写盘。

分别统计：触发至首个有效采样、步骤间隔误差、人工接管至宏贡献清除、失联至主机中和、游戏实际动作成功率。所有同机阶段使用明确单位的单调时钟；跨设备端到端延迟按 [validation](validation.md) 外部测量，不能直接相减 Pad 与 Mac 的原始时钟。

“接受触发”“序列执行结束”“出现预期游戏动作”“完美招架 / 闪避成功”是四个不同结果。首版最后一项只作观察，不作为固定宏的承诺。记录游戏 FPS 与串流 FPS，不能用收到的重复视频帧证明调度正确。

## 8. 验收矩阵

下表全部为后续验收要求，当前均未执行。固定构建、存档副本、键位、装备、宏配置版本和采样定义，保留失败样本；同一报告中不得把输入日志代替画面验证。

| 编号 | 场景与最低样本 | 通过条件 |
| --- | --- | --- |
| AC-01 | 离线伪采样器，覆盖五个动作、触发相位和抖动，至少 1000 次确定性执行 | 按键 / 轴组合与步骤顺序符合配置，无丢失释放、重复触发或无界积压 |
| AC-02 | 同键两次短按、后方向＋X 后快速归零、ZL 已保持 / 未保持、冲突轴 | 两次按下之间存在有效释放采样；后翻组合完整；不满足启动条件时拒绝而非产生半个动作 |
| AC-03 | 每个阶段注入取消、人工接管、配置 / 代次变化 | 下一次有效采样没有宏残留；保留当时有效人工状态；右摇杆非冲突输入继续生效 |
| AC-04 | 正常暂停和超过 250 ms 的采样停顿、编码停顿、连续快速触发 | 超时取消；无恢复后补发；编码帧数不控制宏推进；活动数量和步骤预算不超限 |
| AC-05 | 至少 20 次受控断线 / 重连，含静默断网与显式断开 | 满足中和目标；恢复不重复旧动作，不残留按住状态；同时报告误超时与实际测量精度 |
| AC-06 | 五个动作各 30 次真实 BOTW 测试，固定可执行条件 | 每个动作实际完成目标至少 29/30；全部失败保留并归因；招架按动作成立计数，完美反击另列 |
| AC-07 | 客户端动作键、多点触控、已有手柄，至少 50 次动作触发的外部延迟样本 | 专用触发不泄漏；人工接管可用；按 validation 报告端到端分位数，说明宏准备阶段；无宏路径做同条件对照 |
| AC-08 | 两个模拟会话路由测试；再在已可运行的两个真实会话中测试 | A 的触发、取消、重连与配置变化不改变 B 的输入；模拟测试不代替真实双会话验收 |

AC-06 的门槛是首版工程目标，不是当前成功率。掉帧 / 卡顿条件另列压力测试；不通过修改统计口径掩盖失败。功能验收同时检查原有普通输入、退出和断线释放回归。
