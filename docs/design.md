# 项目设计

状态：目标架构，2026-11-02；Rust 原生服务端与离屏输出待实现。既有 USB 输入原型见 [NXB-045](reports/NXB-045.md)，任务状态见 [backlog](../tasks/backlog.json)。

## 问题与目标

Pad 本地 BOTW 路线未达到目标。NXBridge 把运行游戏的工作放在 Apple Silicon Mac，Pad 负责视频解码、显示和输入。优先完成家庭局域网内稳定、可恢复的游戏会话。

用户指定 NX2Apple / nxnative 作为游戏运行路线。NXBridge 接管构建编排、启动和会话管理，复用既有构建工具与 nxnative 引擎。目标采用 Rust 实现 Moonlight 兼容的 GameStream 服务端，接收运行时离屏帧与 PCM；正式运行时无需 NX2Apple GUI、独立 Sunshine 或可见游戏窗口。游戏渲染器继续由 nxnative 承载。

Sunshine 保留为基线与过渡，Moonshine 是 Rust 协议复用候选，其 Linux 平台依赖需要拆分。首个原生版本运行于已登录的 macOS 用户会话；无显示器、锁屏、未登录能力独立验证，见 [服务端设计](game-session-server.md) 和 [ADR-0002](decisions/0002-rust-offscreen-server.md)。

家庭有 2–3 位玩家。本设计按“同时独立游玩”预留完整隔离，并支持“轮流游玩，各自进度”。具体使用方式尚待用户进一步确认；并发游戏数量不是已实现承诺。BOTW 的多个实例各自运行单人游戏，不会因此变成游戏内联机合作。

长期产品愿景是“Mac 作为家庭共享的原生游戏主机，Pad 作为个人入口”：玩家独立进度、设备切换后接回保留会话、主机自动接纳或排队。以稳定游玩与可恢复体验证明价值；Rust 和离屏输出为这些能力服务。跨主机运行中迁移与引擎重写不进入首版范围。

产品按多游戏设计，BOTW 是首个完整链路验收对象。其他游戏使用独立的构建、运行与输入配置，完成逐游戏验证后进入可用游戏库。后续提供内置 Web 管理界面，Web、CLI 和 agent 共用 Host 管理 API；日常游玩继续使用 Moonlight。页面范围、存档版本兼容和实施顺序见 [Web 管理与多游戏支持设计](web-management-and-game-library.md)。

## 用户流程

1. 家庭管理员在 Mac 配置已准备好的游戏构建，确认本机可以正常游玩。
2. Pad 与主机配对，选择玩家档案和游戏。
3. 主机检查存档锁、主机容量及渲染 / 编码资源；足够则创建会话，否则显示排队或其他主机。
4. Pad 进入自己的画面；目标原生模式不在 Mac 显示游戏窗口，触屏控制和外接手柄均绑定该会话。原版 Moonlight 的玩家入口与多会话端点兼容尚待验证。
5. 短暂掉线立即释放按键，保留会话供原客户端重连；重新接入需重新确认控制权。
6. 退出时允许游戏完成保存，再结束该会话；退出不删除玩家档案。

## 范围

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 环境与本机 | 可重现的版本、路径、BOTW 固定存档测试 | 本机游戏性能有原始数据 |
| 协议与输出原型 | Rust 合成音画服务端；nxnative 离屏帧 / PCM 输出 | 分别验证 Moonlight 兼容、游戏时序与安全缓冲复用 |
| 单会话原生串流 | 无窗口真实游戏、音频、LAN 触屏 / 手柄输入 | 达到单会话质量目标，并与 Sunshine 基线对照 |
| 多实例验证 | 两路、再三路独立会话 | 每路达标且不存在跨玩家读写 / 控制串线 |
| 家庭可用 | 玩家档案、排队、重连、退出、启动入口 | 恢复与长期运行验证通过 |

首版不承诺公网连接、跨平台主机、任意游戏支持、HDR / 4K、游戏内联机、多租户安全沙箱。体感与震动单列验收，基础按键可用不等于 BOTW 全部体感玩法可用。

可选输入增强按 [输入桥迭代需求](input-bridge-requirements.md) 推进：BOTW 后翻、左右侧跳、招架和滑盾由主机执行有限动作序列，玩家掌握触发时机并可随时接管。自动完美盾反、完美闪避与游戏状态识别为后续候选；动作宏不阻塞基础音画和原生串流验收。

## 成功标准

[验证文档](validation.md) 定义具体指标。核心是每位玩家都获得合格的游戏帧时间和操作延迟，测试含户外、持续运行及重连。串流界面的 60 FPS 计数不能证明游戏运行 60 FPS。

[本地配置示例](../config/local.example.json) 中初始并发上限为 1。双开、三开的容量门槛通过后再提高；容量不足时保留排队机制，也预留把独立实例分配到另一台 Mac 的接口。

## 设计原则

- 复用游戏引擎、协议实现候选、编解码与客户端，将自研投入集中于 Rust 会话服务和 Mac 适配；协议复用程度由原型验证。
- 性能目标可度量；未测试的 API 组合用“候选”或“待验证”标记。
- 主机保持独立部署；控制层不进入每帧视频处理热路径。
- 可写数据按玩家 / 会话隔离；只读资源按内容版本共享。
- 同用户多进程提供逻辑和故障隔离，不宣称抵御同一 macOS 账户下的恶意程序。
