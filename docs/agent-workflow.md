# Agent 工作流

工作模式：一个 agent 可完成设计、实现、验证和评审这些阶段。阶段名称不意味着自动启动多个子 agent。具体授权规则见 [AGENTS.md](../AGENTS.md)。

## 任务状态

[backlog](../tasks/backlog.json) 是唯一状态源。

```text
todo -> in_progress -> done
             |
             +-> blocked -> in_progress
```

`blocked` 必须附上具体外部依赖、证据和解除条件；`skipped` 必须说明由哪项决策替代。依赖尚未完成的任务可以做只读准备，但不能冒充已通过对应里程碑。

## 一个执行循环

1. **恢复**：读取当前状态、待办和 Git diff。识别本次用户指令是否调整了目标、设备或约束。
2. **领取**：选择一个依赖满足的任务，写 owner 和 in_progress。先确认要改变什么，以及何种证据才能完成。
3. **准备**：固定上游版本，检查设备身份、路径、存档副本和其他运行会话。不要为准备实验修改未授权的系统设置。
4. **实施**：小步实现；任务涉及架构变化时先更新相关决策与接口，保留现有工作。
5. **验证**：运行最小充分检查和验收；为故障隔离、丢连接释放等重要行为写测试，文案修改只做文档检查。
6. **评审**：核对需求覆盖、回归、失败路径、性能口径、未恢复的实验设置。没有另一个 agent 时执行自审。
7. **交接**：更新任务证据、当前状态和下一步。最终回复说明结果、测试、限制与可点击文件位置。

## 文档与代码协作

- 产品范围变更写入 design；模块与边界写入 architecture；实例身份 / 生命周期写入 sessions；状态仅写 backlog。
- 只有重大且影响未来选择的取舍新增 ADR，普通实现细节写任务记录即可。
- 上游快照是研究参照，实际构建在第一次验证时形成兼容版本记录，不自动跟随 main。
- 新任务使用明确 ID、依赖和验收条目。不能只写“优化性能”，应说明场景、目标和证据。
- 说明 planned / implemented / measured 的差别，避免后续 agent 把文件名、配置示例或函数声明当作功能完成。
- `make check` 是文档和元数据检查；后续每个模块补充自己的真实构建 / 行为测试命令。

## 持久证据

任务报告按 [模板](../templates/task-report.md) 保存到 `docs/reports/`，只在有实际进展或需要交接时创建。大量原始记录放 `artifacts/<run_id>/` 或仓库外；摘要记录路径、哈希和环境，缺少原始数据时写明限制。

中断前或失败后记录：运行的 PID / 会话、修改过的设备设置、已备份位置、未提交文件、需要恢复的动作。不要在下一次恢复上下文时盲目重启游戏或删除残留目录。

若用户明确要求多个 agent，先分配互不冲突的文件范围；设备、运行实例、存档写者仍由一个负责人串行控制。其他 agent 可做只读调研或离线测试。
