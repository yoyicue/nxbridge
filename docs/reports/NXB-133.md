# NXB-133：时之笛双开线程与内存诊断

日期：2026-11-10。任务状态以 backlog 为准。执行者：Codex。

## 范围

在 NXB-131 的同一新档副本和房间条件下，用两份独立存档、两份缓存副本分别启动 1402 / 1372 的 S2Arm 离屏会话。硬件、系统和构建身份见 [NXB-131](NXB-131.md)。两台实际读回林克房间；这是带探针的诊断，不是性能对照或游戏兼容验收。

两游戏进程分别用 macOS `sample` 采集 5 秒、采样间隔 5 ms；先采 1402，再对它执行一次 `vmmap -summary`，最后采 1372。两个栈样本并非同时取得，且后者受先前诊断扰动。`vmmap` 采集期间 1402 进程约 24 秒未推进，对应视频源时间戳最大间隔约 24.19 秒；这是探针期间的无效性能样本，不能用作真实游戏长帧。1372 同局最终源间隔最大约 5.36 秒，发生在带探针会话，未建立因果，不用于性能成绩。此前无 `vmmap` 的 [NXB-131](NXB-131.md) 结果仍单独保留。

## 结果

- `sample` 输出的 1402 / 1372 物理足迹分别约 9.0 / 8.9 GiB（峰值 9.2 / 9.1 GiB）。它遍历线程时包括等待线程，不是 CPU-only profile。两个样本均可见大量条件变量、信号量等待；这些计数不能当作 CPU 时间。多个客体 `nx-*` 线程进入未符号化的游戏代码，也见命令记录 `cmd_alloc_cb`、地址转换 `nvn_ga2ca` 和 Metal 参数编码 `encode_args` 等路径；采样数不足以断言某项是 CPU 主因。`cmd_alloc_cb` 函数包含游戏命令内存回调逻辑，但出现该函数不证明实际调用了回调；后续计数结果见 [NXB-134](NXB-134.md)。不能通过关闭回调或跳过设备命令来优化。
- 1402 `vmmap` 一次快照报告 `shared memory` 虚拟映射 6.9 GiB、`owned unmapped (graphics)` 虚拟映射 1.8 GiB，IOSurface 10.7 MiB。它同时报告进程约 9.0 GiB footprint；同一页可能有别名，共享映射的虚拟大小不是专用物理占用，分类不可相加。该快照的 `SWAPPED` 口径也不能当作系统磁盘 swap 实写量。
- 引擎日志的 Switch 2 应用池上限为 9,216 MiB，另有一次申请记录包含游戏堆 6,268 MiB、代码等及物理映射账；这是游戏地址 / 池限制和资源记账，不等于同一时刻实际独占的物理内存。结合本轮映射和此前观察，可以优先研究客体内存与图形资源；不能把 9 GiB 全归咎于 NXBridge 媒体帧池。
- 固定上游 `runtime/src/vawin.c` 提供 `S2A_GUEST_FILE` 文件后备，但 macOS 默认关闭；进程 footprint 下降可能只是记账方式变化，并不等于系统内存或磁盘写入减少。上游源码注释记载某些 iPhone 游戏两分钟产生 6–7.5 GB 写入并伴随卡顿，不能将该值外推到本机。当前主机可用空间曾在双开时降至约 12 GiB，文件后备的默认启动检查阈值也是 12 GiB，因此本轮没有强制启用或绕过保护；文件后备与双路收益未知。

## 下一步与边界

下一项应先在独立副本启用上游命令记录统计 `DM_NVN_CMDSTAT`，量化每帧命令数、回调和命令内存增发，并关闭探针重跑性能对照。该统计路径会加锁，需把探针局单独标记，不能直接用探针帧率判收益。只有存在足够明确的调用频次和性能证据后，再考虑针对记录路径的小补丁，保留 NVN 回调、资源生命周期和 GPU 安全保护。若要研究客体文件后备，先准备充足空间并预设写入量、帧间隔、磁盘余量和停止边界；不以 footprint 变化冒充内存削减。

未知：游戏逻辑速度、音画同步、GPU 缺页根因、CPU 各线程实际运行时间和多实例容量。用户存档不随诊断更改。两路实验进程及 worker 已正常退出，服务恢复至两台各自的新档配置；新旧四份存档分别与已有备份哈希一致。栈、映射、截图和诊断会话保存在本机忽略目录 `oot-profile-20261110`。`make check` 与 `git diff --check` 通过；不代表性能达标。
