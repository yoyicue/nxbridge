# NXB-134：时之笛图形命令记录诊断

日期：2026-11-10。任务状态以 backlog 为准。执行者：Codex。

## 目标与方法

根据 [NXB-133](NXB-133.md) 的栈观察，在同一林克房间评估命令记录量及命令内存不足回调频率。双路使用同一 1402 新档的独立副本和缓存副本；1402 使用忽略目录中的临时启动器开启固定 S2Arm 上游的 `DM_NVN_CMDSTAT=1`，1372 使用原宿主。计数器每 300 个源帧报告并重置，有互斥锁和日志开销；开启探针期间的帧率不是性能验收，不与 [NXB-131](NXB-131.md) 的无该探针帧率做因果比较。

两台实际读回相同房间。截图后在 1402 连续取得六个完整的 300 帧统计窗口，帧编号从 3,301 到 5,100；两个 Pad 静止。原始日志区间、图像和会话诊断数据保留在本机忽略目录 `oot-cmdstat-20261110`。

## 结果

- 六个窗口中，每帧记录约 14,313–14,480 条图形命令，宿主记录数据约 466.9–472.4 KiB / 帧；这些是记录量，不是每帧最终图形绘制数或 CPU 耗时。
- 命令内存不足回调均显示 **0.00 次/帧**，宿主借用窗口均显示 0.000 次/帧；这些数字经过格式化舍入，并不能断言绝对零次。该观察不支持把关闭或减少此回调作为当前优化目标。
- 字节量居前的命令包括统一缓冲绑定 `OP_BIND_UBO`（约 2,326–2,346 条/帧）、状态绑定 `OP_BIND_STATE`（约 1,648–1,669 条/帧）和纹理绑定 `OP_BIND_TEX1`（约 1,348–1,365 条/帧）。分类与当前固定上游 `nvn_obj.h` 的枚举一一对应。记录中有大量绑定命令，但没有证据表明可以无条件删除或跨记录合并，须保留命令回放、同步、生命周期和每个玩家的状态隔离。
- 每窗口末上游记录的 live host blocks 约 46.6–47.0 MiB，不代表全部游戏或 GPU 内存；游戏命令段可能反复供给和复用，不能按每帧供给段数与均值简单相乘宣称占用。

本次场景没有支持可安全部署的优化候选；因此没有修改图形后端或更改默认参数。更有价值的下一步是先用生产路径的无探针对照定位绑定记录的 CPU 时间，再仅对语义上可证明冗余的绑定尝试可回退的合并，并以不同资源状态、回调、重放、双会话及画面回归测试约束。游戏速度、音画同步、GPU 故障根因和双人容量仍未知。

后续源码核对：固定上游 `nvn_mtl.m` 的 `state_op` 已对重复的状态、UBO、SSBO 和纹理绑定比较当前值，避免重复标记状态变化；`encode_args_` 也有带失效条件的参数缓冲复用。命令记录阶段的 deferred 绑定和 `OP_BIND_TEX1` 可在回放时读取游戏内存，不能仅依据录制时值删除记录。因此当前没有证据表明再加一层绑定去重安全或有效；停止该方向，不能把命令总数直接当作可消除的开销。

## 恢复与验证

两路诊断游戏与 worker 已通过各自 Pad 正常退出，服务恢复两台各自新档配置；两份新档和两份旧玩家存档均分别与备份逐文件哈希一致。运行中系统曾有较高 swap，退出后已回落；未改动系统内存或 GPU 安全机制。`make check` 与 `git diff --check` 通过；它们不代表游戏性能通过。
