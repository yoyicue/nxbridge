# NXB-111：服务端视频 FEC 与排队优化

日期：2026-11-05。执行者：codex。任务状态以 [backlog](../../tasks/backlog.json) 为准。

## 目标与范围

针对视频冷 FEC 初始化耗时和多级队列积压，减少服务端 CPU 等待与旧画面排队。保留 H.264 参考帧顺序、当前画质、游戏设置和媒体协议。实际 BOTW FPS、Pad 呈现和 input-to-photon 仍由 NXB-107 / NXB-037 验证。

## 最终变更

1. 纳入有来源与 BSD-2-Clause 声明的 `fec-rs` 0.1.0，增加直接构造系统矩阵的 API。旧构造先生成、求逆 Vandermonde 矩阵，随后覆盖校验行；新路径直接生成单位数据行和协议指定的 Cauchy 校验行。编码、SIMD、并行阈值及恢复算法不变。两个 Cargo 入口均使用同一本地补丁，来源见 [NOTICE](../../vendor/fec-rs/NXBRIDGE-NOTICE.md)。
2. 视频矩阵改为进程内最多 128 个条目的 LRU 缓存；条目只保存编码器矩阵，不保存玩家数据、密钥、IV 或 RTP 序号。构造在缓存锁外执行，移除每次会话预填 64 个规模的预热；打包仍在每路一个 awaited blocking job 中执行。
3. 收紧各级视频排队。编码后的帧与批次按顺序交付，不为追赶时钟跳过 P 帧；发送完成确认表示本地 socket 调用结束，不是客户端收包或显示确认。取消可中断入队和完成确认等待。

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| Rust 编码帧通道 | 4 个排队槽 | 1 个排队槽；生产者仍可能持有一个正在等待入队的帧 |
| UDP 前批次 | 3 个排队槽，另有活动发送 | 总共 1 个待确认批次；确认前不打包下一帧 |
| 原生 worker 待提交画面 | 3 个原始帧 | 最新 1 个原始帧；替换旧帧并释放其精确租约 |
| 原始帧过期 | 没有排队时间限制 | 提交 VT 前检查，排队超过 66.7 ms 则释放；没有新帧时也不会补编码这个旧帧 |
| worker → Rust 视频字节流 | 系统默认缓冲 | 发送和接收端各请求 32 KiB；大关键帧分段通过，不截断数据 |

VT 在途上限仍为 2，源 IOSurface 池仍为 6。上述限制不是端到端延迟上限；VT、内核、网络和客户端仍有各自的等待。

4. 补充诊断点。Rust 每 10 秒记录通道等待、打包（含 blocking 调度）和本地发送交付的窗口最大值；worker 定期记录生命周期内的源 PTS 间隔、接收间隔、原始帧等待、VT 提交到回调、序列化 / pipe 写入耗时，以及过期 / 替换计数。源 ready 间隔不能直接等同于游戏仿真 FPS，VT 回调时间也不是纯 GPU 时间。

## 结论与限制

已消除大规模冷 FEC 构造的主要冗余，并把背压更早传回可安全舍弃的未编码画面。没有修改游戏渲染、shader、分辨率、码率或 VT 低延迟选项。仍需测量真实网络阻塞时的积压消退，以及实际游戏与客户端的长帧、音画同步、端到端延迟。

部署时 ADB 没有在线设备，因此没有新的 Pad 体验、稳定 30 FPS 或并发容量结论。更浅的队列可能在调度抖动时丢弃更多原始帧，实际平滑度和延迟需要同场景实测。新增阶段日志为下一次定位提供数据，不替代外部延迟测量。
