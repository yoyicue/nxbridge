# NXB-117：游戏库封面与自动刷新

日期：2026-11-09。状态以 backlog 为准。执行者：Codex。

## 目标与范围

把 BOTW 和 TOTK 的封面从手工维护的串流配置迁到本机游戏库，且后续换图无需重新安装客户端或手动删除缓存。此任务只验证封面、应用列表和已有入口，不启动游戏或改变存档。

## 最终变更

Host 游戏库为每个游戏管理独立 PNG，管理台支持预览和更换。上传限制为小于 5 MiB、最长边 4096，检查图片解码，使用游戏 ID 作为路径，并以 SHA-256 作为版本；更新带旧版本比较，冲突时不覆盖，封面文件原子替换。旧 catalog 无需迁移字段；现有游戏 ID、构建和存档不因换图改变。

两路 GameStream 映射到同一游戏库封面目录。标准 `/appasset` 仍返回原图；应用列表增加可选的 `NXBridgeCoverVersion`。定制 Moonlight 327 对内容哈希进行验证，成功时原子替换缓存，并处理内存中 A→B→A 的回切；原图保留在本机，未编辑或加入 APK / 仓库。服务端启动映射尚需配置，完整 Host 生命周期和游戏入口管理尚未统一。

## 验证证据

- 在 1402 与 1372 均通过 xpad2 受管安装客户端 327，保留应用数据；安装前各自的 325 APK 已备份。验收中先安装 326，发现 A→B→A 内存命中会让磁盘停留 B，修复后安装 327 重测。
- 使用 Host API 将 BOTW 原图 A 换为本机既有旧图 B，再恢复 A；两台前台游戏列表均自动更新磁盘缓存，分别在轮询后约 22 秒和 28 秒完成，无重新安装、手动清缓存或 ADB reverse。两台截图均显示恢复后的原图；1402 仍显示 BOTW 和 TOTK 两入口，TOTK 缓存哈希未变。第二台保留其原本的 BOTW 单入口。此次未启动游戏。
- BOTW 和 TOTK 图像迁入游戏库后的 SHA-256 与原文件一致，管理台页面经 Chrome 无头截图核查，两图和更换入口显示正常。通过脚本测试页面上传请求，通过本地真实 HTTP 测试二进制上传、来源限制、无令牌拒绝、版本冲突与读取。
- Rust 测试覆盖旧 catalog、缺图 / 旧图路径缺失、损坏图片、大小及路径校验、版本更新和并发竞争；客户端补丁在固定上游 325 实验树重放，八个文件与实际构建文件逐字节一致，Android `:app:assembleNonRootDebug --offline` 成功。`cargo test -p nxbridge-host -p nxbridge-gamestream --offline`、`make check-rust`、`node tests/dashboard_ui_test.cjs` 和 `make check` 通过。`make check` 只是项目元数据检查。
- 本机 `.nxbridge/experiment-117/` 保存原图、旧配置、旧 APK、安装日志和截图；游戏资源、图片、密钥与存档不进入源码提交。

## 结论与限制

自动刷新仅在 NXBridge 定制客户端 327 上实机验证。标准 Moonlight 会忽略扩展字段，旧缓存不会因此自动失效。离线或下载失败时，客户端保留已有磁盘图，重新进入列表可重试；若从未缓存则显示占位图。无封面时不发送版本，已有缓存可能继续显示。客户端网络中断和下载时版本竞态按实现检查，未做独立的断网故障注入；并发上传竞争由服务端测试覆盖。轮询约 30 秒，不保证即时刷新。

上游应用 ID 仍由串流标题生成，改变封面不改变 ID，但改变串流标题可能改变入口 ID；游戏库的 ID 不能被误认为已完成全链路稳定身份。此项不证明任何游戏的输入、保存、性能或多会话能力。
