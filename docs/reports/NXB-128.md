# OoT 缓存、预热与音频排队优化

日期：2026-11-10。基线为 NXBridge `16e87f0`、S2Arm `93bf8c6cab24934b3fe05af4bc04cba1fec84328`。任务状态以 [backlog](../../tasks/backlog.json) 为准。本轮交付缓存、预热、编译调度与音频排队改进，并记录仍存在的首遇长帧和游戏时序风险；不能据此宣称稳定 30 FPS 或其他游戏已经兼容。

## 已确认的问题

NXB-127 私有暖缓存样本的预设 120 秒区间有九个超过 100 ms 的原生帧，九个均记录了新 shader library / pipeline 创建。最长一帧约 1.377 秒，其中 GC 暂停约 43.677 ms；另八帧未记录 GC 暂停。这是定位线索，不能把并行编译各项耗时相加作为独占关键路径。

公开启动器原先把翻译缓存放在新会话下，不能跨重启复用。固定上游的 `warm_paths` 还会在离线 seed 清单缺失时返回空，即便本机已有真实 `pso_user.tsv`。上一轮仅复制 MSL / JSON，因此没有实际预热，也没有留下 Metal binary archive。

## 当前改动

- `DM_TEMP/.s2arm-cache/<identity>` 保存翻译结果、管线记录和归档；每次会话仍有独立日志目录。身份包含准备清单、宿主二进制、游戏模块 / NPDM / 资源索引 / shader 索引及系统架构与版本。逐 shader 的 chain / translator 指纹检查及 Metal archive 的实际 GPU / OS / chain 检查继续生效。
- 缓存入口采用独占锁、完整目录原子发布和跨 `exec` 保留锁；拒绝符号链接和不匹配身份。只恢复完整换行的管线记录，崩溃留下的半条 append 不进入下一次追加。原生 shader 与 archive 文件继续使用上游临时文件加 rename 的发布方式。无缓存迁移或自动清理旧构建的行为。
- 修复缺少离线清单时忽略本机记录的问题；实际预热仍通过上游校验与解析。首帧准备最多四个 worker、15 秒截止，剩余工作交给两个后台 worker；沿用上游同键编译去重与首次使用优先机制。截止时已开始的准备任务会完成，短时并发不能只按两个后台 worker 计算。
- 修正 archive 临时目录清理边界：不能依据共享目录中“新出现的文件”就认定属于本进程；其他应用不一定遵守 S2Arm 的锁。无 bundle 的宿主保留这些共享临时文件，空间占用须继续测量。
- 音频增加队列深度、峰值年龄、背压时间、时钟重置与托管内存读数。前三轮缓存实验宿主使用原先 320 ms 的渲染器排队上限；独立构建的候选改为 80 ms 背压，常规 5 ms PCM 包在达到该水位后等待真实消费，不丢包或提前完成。较大的合法 AudioOut 包允许独占进入空队列，保留 64 个描述 / 2 秒 PCM 硬边界。候选同时将混音缺口与各 session 欠载分开统计：上游会常开未使用的 renderer session，后者不能代表可听缺口。菜单、森林及长时间观察结果见下文。

实现位于公共适配路径，没有 OoT 标题 ID、游戏地址或专用 shader 白名单。其他接入该后端的游戏可复用机制；收益和兼容性需要各自验证。原有 nxnative 后端不会自动获得这部分改动。

## 实机验证与限制

首轮冷启动在固定路线开始前触发 SSD 余量保护，样本无效。采样的游戏物理占用峰值约 8.594 GiB、磁盘余量最低约 2.029 GiB；高压力下采样间隔变长，超过 3 GiB 的停止边界后才取得下一次读数。该轮没有连续系统 swap / 编译服务占用记录，不能断言全部空间消耗来自游戏。守护进程先请求退出，超时后强制结束自建测试进程组；原有四个 Host / GameStream / Sunshine 进程及启动时间均未变。

同一轮压力期间，截图解码超过 10 秒，启动锁测试有一项等待缓存创建超时；测试实例退出后，14 项启动测试在 0.980 秒通过。该次失败保留，不作为功能回归失败的确定归因，也不能把压力期间的结果删除后宣称全部测试一直通过。

第二次启动成功复用首轮实际留下的记录：预热 825 个 shader、609 个 render pipeline、88 个 compute pipeline，约 11.576 秒完成；首帧准备等待约 11.244 秒，其余后台收尾，697 个管线归档写入完成。它证明预热和归档生成路径已经执行，尚不是下一次归档命中或稳定 FPS 的证据。后续观察已加入逐进程物理占用、系统 swap 及主要后台进程记录；强制退出改用逐个核对启动身份的自有 PID。

该轮 480.106 秒到期正常退出，视频收到 25,034 帧、编码 13,349 帧、丢弃 11,685 帧、失败 0、在途 0；音频 94,840 块全部释放，52 次 discontinuity，桥接丢弃 0。这是原生 worker 链路，不是 Pad 实测。预设路线 120.196 秒内记录 6,215 个原生呈现间隔：平均 51.70 FPS，P50 / P95 / P99 为 18.468 / 23.008 / 35.670 ms，11 次超过 100 ms，最长 471.017 ms；其中十次仍伴随新 shader / pipeline，一次没有。路线内游戏物理占用峰值约 9.031 GiB、worker 约 8.376 MiB、swap 最高约 9.712 GiB。游戏时序与客户端显示帧率未知，不能宣称稳定 30 FPS。

随后再启动已实际命中 697 个 pipeline archive，其余新记录的 153 个编译；预热 shader 886 个、render pipeline 761 个、compute pipeline 89 个，约 11.611 秒完成。首次使用归档与继续收集新管线同时存在，仍需重复同一路线及长期观察。

第三轮在相同存档副本执行同一输入路线，120.247 秒记录 6,009 个间隔：平均 49.97 FPS，P50 / P95 / P99 为 19.269 / 23.744 / 29.942 ms，3 次超过 100 ms，最长 1,069.064 ms，三次均有新 shader / pipeline。全局复用 884 个 shader，另现编 12 个、失败 0。与上轮相比，长帧次数减少但最大停顿变长，且系统 swap 不同，不能据单次结果宣布整体提速。游戏物理占用采样峰值约 9.179 GiB；路线内 swap 最高约 4.863 GiB。游戏 / worker 最终正常退出、视频失败 0、在途 0、PCM 93,737 块全部释放，25 次 discontinuity，桥接丢弃 0。两轮都没有操作 Pad。

额外只读 `vmmap` 显示这款游戏的主要占用在 guest VM / shared memory，媒体 IOSurface 约 10.7 MiB；原生日志记录游戏堆约 6.268 GB。不同映射可能指向同一物理页，不能将这些分类直接相加。缓存机制已经生效，但未消除未遇到的管线编译，也没有证明游戏主体内存显著减少。

使用同一森林存档的独立副本，先记录冷启动，再复用本轮实际产生的缓存做暖启动；固定 120 秒输入路线在画面确认后开始。需要继续对比长帧、实际 archive 命中、原生呈现、游戏速度、客户端显示、独立进程物理占用及 swap。原始样本、游戏资源与操作凭据只留在忽略目录。

两轮缓存宿主均已退出。80 ms 候选的冷启动在森林加载阶段再次达到磁盘余量保护：350.280 秒退出，游戏物理占用峰值 8.619 GiB、最低 SSD 余量 2.963 GiB、最高系统 swap 12.167 GiB；没有执行固定路线。上游优雅退出超出内部 1.5 秒期限后退出，worker 返回 0 不能将样本改判为成功。该轮现编 756 个 shader、失败 0，视频失败 0、在途 0，66,023 块 PCM 全部释放；菜单阶段的队列上限符合 80 ms 候选，不能推导森林音频或端到端延迟已经改善。

Pad 之前关停的 33 个 `bridge_other` 均出现在控制连接超时之后，错误为已关闭接收端的 socket 错误；视频尾部失败具有相同生命周期边界。Rust 桥原先先终止接收 task，再停止仍在发送的 worker。现在先通知会话停止投递，继续读走 worker 的尾部音视频，再在其退出 / 既有 5 秒截止处理后释放接收端。两个保留接收端的负对照在旧行为失败；修正后 GameStream 17 项通过，包括消费端关闭、视频队列满时关停唤醒及输入重连中和。测试里的突发 PCM 曾触发 Darwin `ENOBUFS`，测试现仅重试容量压力，不忽略接收端关闭错误。真实 Pad 长时间串流与断开结果见下节。

最终候选的 GPU 反馈 22 项、输入 20 项、音频 73 项、四种 Metal 3 / 4 合成视频路径、原生媒体回归均通过。上游 `contrib_check` 仍在未提交的适配副本门禁处退出 2；首次默认 PATH 另报依赖版本不符，改用实际构建工具链后工具检查全部通过，仍不能将未运行的后续门禁列为通过。适配源码完整重放与过程中的 `make check` 已通过，不能代替最终变更后的完整检查。

## 长时间串流与关停

80 ms 候选在 1402 完成从森林画面开始计时的 1,865.715 秒连续观察，使用隔离服务及存档副本；每两分钟交替转动视角，每分钟采样客户端覆盖层，并保留少量截图。这是单场景、带探针的运行观察，不是无探针正式性能验收。预热本次实际编译并写入 553 个管线归档，游玩期间继续遇到新 shader。

| 指标 | 实测 |
| --- | --- |
| 原生呈现 | 98,756 个连续间隔；平均 52.93 FPS |
| P50 / P95 / P99 | 18.341 / 22.022 / 32.723 ms |
| 超过 100 ms | 14 次，最长 2,080.643 ms；滑动 1 秒窗口最低 0 次呈现 |
| 客户端 | 31 次覆盖层样本为 29.34–31.07 FPS；没有连续显示帧轨迹 |
| 游戏 / 服务 / worker 物理占用峰值 | 约 9.206 GiB / 9.547 MiB / 8.704 MiB |
| 系统 swap 峰值 / SSD 最低余量 | 约 10.233 GiB / 3.784 GiB |
| 路线内托管分配 / GC 暂停合计 | 639,805,120 字节 / 162.187 ms |

14 个长帧中，12 个记录到新 shader library / pipeline；一个 117.378 ms 帧未见编译或 GC，另一个 245.396 ms 帧没有对应的详细长帧日志，不能归因。此次没有 GPU 安全停机或资源保护退出，但长帧确实存在，不能用平均值或客户端覆盖层宣称稳定 30 FPS。

音频常规队列观测到 3,600 帧、峰值 3,840 帧，即约 75 / 80 ms；此前 320 ms 实现的峰值为 15,360 帧。候选的实际混音欠载保持在启动阶段的 720 帧（15 ms），未随森林观察增加；未使用 session 的欠载另计。加载过程中队列峰值年龄仍达到 969.049 ms，最大时钟迟到 887.962 ms；全程 PCM discontinuity 为 146 次。减少排队不等于消除调度停顿，也没有完成听感或音画同步验收。

观察结束时，在触屏转动视角过程中强制停止测试客户端。游戏和 worker 在命令开始后约 5.390 秒均退出，游戏记录正常优雅关停；worker 视频失败 0、在途 0，413,884 块 PCM 全部释放，`bridge_dropped` / `bridge_other` 均为 0。它验证了保留接收端直至 producer 退出的修正，而不是将错误计数忽略。输入轨迹的最后一个非零状态至中立为 215.767 ms。Python 的 `monotonic_ns` 与原生 `CLOCK_MONOTONIC` 在本机约有 1 秒偏移，不能直接相减；因此不报告未经同步的“强制停止命令至中立”延迟，以上输入间隔来自同一原生时钟。后续运动对照已统一使用 POSIX `CLOCK_MONOTONIC`。

隔离服务及日志采集已退出，1402 的 13 个持久文件逐一恢复 SHA-256 校验一致，三个输入法设置也恢复原值；原四个服务的 PID 和启动时间不变，测试存档锁已释放。1372、原游戏资源及原存档未操作。

随后 80 ms 候选从原始检查点副本重复预设 120 秒路线：启动命中 553 个管线归档，另外编译 311 个；909 个 shader、775 个 render pipeline、89 个 compute pipeline 的预热约 13.287 秒完成。路线 120.205 秒记录 6,160 个原生间隔，平均 51.25 FPS，P50 / P95 / P99 为 18.758 / 23.449 / 32.118 ms，仍有 3 次超过 100 ms，最长 1,094.028 ms；三次均伴随新 shader / pipeline。路线内分配约 146.3 MB、GC 合计 46.704 ms，游戏峰值约 8.898 GiB、worker 约 8.172 MiB、swap 最高 4.207 GiB。后台负载与前几轮不同，不能据此宣称整体提速。

该候选路线所在会话受控退出，视频 14,200 帧中编码 7,895 帧、丢弃 6,305 帧、失败 0、在途 0；56,317 块 PCM 全部释放，13 次 discontinuity、桥接丢弃 0。复用 889 个 shader、现编 14 个、失败 0。这说明已观察内容的缓存可以复用，但覆盖仍不完整。

## 游戏速度诊断

使用两个相同原始存档副本，分别在常规呈现及私有 `S2A_FPS=30` 上限下执行六次交替移动、六次交替转视角，各按 1.8 秒、松开 1 秒。公共启动器和宿主未增加锁 30 帧配置，诊断会话不能计为性能通过。两次开始及结束均有画面确认，期间没有菜单、场景切换或跌落。

离线逐帧解码与 worker 的源 PTS 一一对应，输入边界与 PTS 同为 POSIX `CLOCK_MONOTONIC`。参考固定上游 [自动玩家的运动探测](https://github.com/jhaizhou-ops/S2Arm/blob/93bf8c6cab24934b3fe05af4bc04cba1fec84328/tests/autoplay/autoplay.c)，在 128×72 亮度图上做二维块匹配，取间隔 0.18–0.30 秒的样本，去掉两端各 20%；每次推动至少五对才有效。正常组首个移动只有三对，已排除其运动值；其余 23 次推动各七对。合成静止、正负二维位移和无纹理拒绝检查通过。这是私有的两局诊断，不冒充上游同局开 / 关 / 开判定工具的原始输出。

| 操作 | 上限组 / 常规组原生 FPS | 画面运动速度比（常规 / 上限） | 结果 |
| --- | --- | --- | --- |
| 移动 | 30.00 / 42.01 | 1.507 | 超过上游相对速度阈值 |
| 转视角 | 30.00 / 45.83 | 1.654 | 超过上游相对速度阈值 |

两项都提示运动速度随呈现帧率变化，不能宣称游戏时序通过。它不能确定相对真实 NS2 的绝对 1× 速度，也不能仅据额外上限试验归因于 `S2A_FPS60`：两局仍启用该开关，日志都记录游戏交换间隔 1。后续应单独核对游戏原始节拍、逻辑步进与呈现的关系，再决定是否需要游戏构建专属的时间步修正；不能全局篡改客体时钟，也不能将客户端 30 FPS、原生呈现 FPS 和游戏速度合为一个指标。两次诊断会话均受控退出。

## 补充冷缓存路线

最后另建空的应用缓存工作目录，不迁入此前的 shader 或 pipeline 数据；系统 Metal 缓存保留，故不能称为整机首次运行。宿主确认缺少本机预热清单，整局实际现编 889 个 shader、复用上局 0、失败 0。没有删除构建缓存或停止其他应用来增加余量；本轮开始时系统可用空间与先前无效冷启动不同。

该轮从同一原始存档副本执行相同 120 秒输入：120.222 秒记录 6,307 个原生间隔，平均 52.46 FPS，P50 / P95 / P99 为 18.378 / 22.606 / 30.807 ms，10 次超过 100 ms、最长 466.833 ms，十次均伴随新 shader / pipeline。路线内分配约 211.2 MB、GC 合计 58.668 ms。加载阶段另有 13,018.432 ms 长帧，记录到 121 个新管线、60 个 shader library；该帧 GC 暂停 384.570 ms、GPU 读数 79.785 ms。并行编译耗时不能直接相加作为关键路径，加载长帧也不能从结论中隐藏。

整局 326.842 秒受控正常退出，无安全停机。游戏物理占用峰值约 9.265 GiB、worker 12.376 MiB，swap 最高 10.017 GiB、SSD 余量最低 17.596 GiB。视频 14,877 帧中编码 8,091 帧、丢弃 6,786 帧、失败 0、在途 0；63,887 块 PCM 全部释放，111 次 discontinuity、桥接丢弃 0。队列峰值仍为 80 ms，但加载停顿下峰值年龄达到 2,129.709 ms，不能宣称音频时延已达标。

冷 / 暖固定输入路线分别有 10 / 3 次长帧，但最大停顿和平均帧率未同时改善；背景负载不同，且按时间输入在不同帧率下造成的最终位置 / 视角存在偏移。因此这不是严格的性能 A/B，也不支持固定百分比的提速结论。它与跨重启的 shader / archive 命中记录一起证明机制执行，覆盖和最终体验仍需另验。

## 交接

实现不含 OoT 专用地址或着色器名单。缓存身份、原子发布、缺 seed 时的本机预热、有界后台编译和音频背压已具备回归及实机证据；游戏主体内存仍约 9 GiB，GC 主因与首次翻译重合，不能宣称已全面削减 VM / GC 开销。更多场景的编译覆盖、正常游戏速度及音画同步由后续 NXB-129 跟进，其他游戏逐款验收。

全部自建测试游戏、worker、隔离服务和日志采集已退出；1402 的客户端文件与输入法恢复校验通过，原四个服务保持原 PID / 启动时间。原始证据、实际填写的实验记录、游戏数据和私有构建仅保存在忽略目录。本轮未部署替换原 BOTW / TOTK 服务。

最终候选与从固定上游全新重放副本的 23 个适配文件清单一致；宿主和本轮 GameStream 二进制哈希已记录。9 轮实际实验已填写统一实验记录；原检查点的 31 个文件 SHA-256 再次一致，9 份测试存档的写锁均已释放。最终 `make check` 通过（97 个 Markdown、59 项任务），候选内容扫描 386 个文件、0 项发现，`git diff --check` 通过。前述功能回归结果仍有效；上游完整门禁和 Metal 3 计数器的已知限制没有被改判为通过。
