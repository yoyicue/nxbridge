# NXB-131：时之笛单路与双路隔离对照

日期：2026-11-10。任务状态以 backlog 为准。执行者：Codex。

## 目标与范围

用同一份《时之笛》存档的独立副本，比较林克房间静止画面的单路和双路表现，定位上次双开卡顿的可能方向；这不是 NXB-070 的并发容量或可玩性验收。

M4、16 GiB，macOS 26.5（25F71），NXBridge 基线 `16e87f0` 加当前工作区未提交的 S2Arm 适配；S2Arm 固定修订 `93bf8c6cab24934b3fe05af4bc04cba1fec84328`。两台使用 Android 实验客户端与 Rust GameStream、S2Arm 离屏帧，串流配置为 1280×720、H.264、30 FPS、5 Mbps；实际客户端显示、游戏速度和音画同步未测。

## 验证与结果

先正常退出上轮两路新游戏，备份两份已退出存档并逐文件哈希核对；原来的两份玩家存档也分别与备份一致。取 1402 的 19:22 自动存档制作两个独立副本，复制同一份已热缓存作为两路起点，分别运行在不同目录和独立会话。1402 及 1372 均实际选择并读回该副本，显示同一房间。**没有用 1372 自己的新存档副本做读档回归**，不能由此证明它的读档能力。

先采 1402 单路，之后保持 1402 运行并启动 1372，二者读回房间后再同步采样；均不操作人物，各采约 60 秒。开始和结束截取各自 `frames.tsv` 字节位置，统计区间中完整行的 `wall_us`，即宿主 present 间隔，非 Pad 显示帧率。记录线程和 `vm_stat` / swap 每 5 秒采样，测试前后各有截图，存在少量采样扰动；采样期间不截图。原始记录和截图留在本机忽略目录 `oot-compare-20261110`。

## 限制

该次结果支持在相同房间和本机背景下，双开明显降低原生呈现速度并伴随 swap 上升；尚不足以确定 CPU、GPU、换页或上游缺陷各自的因果。没有做交替重复、动态移动、客户端连续显示、延迟、音画同步或游戏正常速度对照；两窗口的启动时间、缓存热度和系统背景不完全相同。此前时序诊断显示游戏速度可能随呈现帧率变化，不能把此处的 43 FPS 直接解释为正常速度的 43 FPS 游戏。未复现上次 GPU 缺页，也不能声称已经修复。

## 恢复与交接

两路实验会话已通过各自客户端退出，确认对应游戏和 worker 进程结束；服务已恢复为上轮两台各自的新档配置，处于空闲状态，原始玩家存档未被覆盖。两份新档和退出后备份都保留；重启至日常启动脚本会回到旧玩家存档，而不会自动选择这些新档。后续应在不复用真实档案写者的前提下，交替重复并针对 CPU / GPU / swap 做阶段归因。`make check`、`git diff --check` 均通过；这些检查不代表游戏性能达标。
