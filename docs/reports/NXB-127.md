## 最终变更

新增 [S2Arm 适配目录](../../adapters/s2arm/README.md)、[修订锁](../../config/s2arm-experiment-lock.json)、准备 / 启动脚本及回归。准备脚本固定提交、不覆盖目标、记录文件哈希；启动脚本隔离会话环境与目录，在启动写入前检查上游着色器链，持有跨进程的存档排他锁。

输入实现 S2Arm 的真实手柄读取钩子；音频工厂接入有界、按消费时钟完成缓冲的 PCM 设备；无窗口呈现分支沿用上游 Metal 队列、生产者事件及完成栅栏，输出 IOSurface，复用 NXBridge 媒体管道。游戏侧与传输协议没有增加游戏专用兼容假象。

补充压力用例时发现：帧槽耗尽后直接跳过新帧，会让上游的完成序号越过仍等待生产者事件的旧帧，导致等待提前返回。修复为在呈现线程上等待旧 GPU 提交完成，再交回跳帧完成处理；避免源纹理过早复用。修复前同一断言仅等 0.3 ms，修复后两种 Metal 后端均等待预期的约 300 ms。

检查上游 `Saves.cs` 后确认 `S2A_SAVE_DIR` 是会清空目标再拷入的启动种子，不能用于持续保存。适配显式禁用它，使用玩家 `DM_SAVE/ryu` 作为跨会话的 `S2A_RYU_DATA`；临时诊断、shader cache 按会话生成。

实际游戏另暴露三处适配问题，均保留修复前、修复后和回退负对照：

- 上游 `HardwareDeviceImpl` 轮换复用四个 `AudioBuffer` 与一个 PCM 数组。适配原来拒绝未消费描述对象的再次提交，约 8 秒即崩溃。现按每次提交复制 PCM，记录各自完成位置；借用客体内存的重复提交仍拒绝。
- Python 启动器用子进程执行链检查，会丢失继承的 Mach 媒体端点。现以 `runpy` 在进程内执行同一只读检查，并使用过滤后的环境。原生及 sandbox 两条测试均实际发送 / 接收 Mach 消息，旧启动器均失败。
- 冷编译进入后续场景时，音频消费者落后，运行中的第 65 个缓冲触发队列上限异常。现保持原容量，通过释放锁的条件等待向生产者施加背压，消费 / 关闭后唤醒；不扩大队列、不假报已播放、不吞掉 PCM。队列满关闭、样本顺序及真实上游描述对象复用均有回归。

## GPU 安全停与后续定位

第一条安全停原文：`frame 20895 kept the GPU busy 1020 ms (limit 1000 ms)`。固定上游的 `graphics/nvn/gfx/nvn/nvn_mtl.m` 中，`gpu_tag_done` 累加归属同一帧的命令缓冲 GPU 时间，超过 1,000 ms 调用 `mtl_gpu_halt`；本轮经该路径停止提交并优雅关停，返回码为 0。不是 600 秒测试截止，也不是编码器报错。

安全停前日志显示：第 20,861–20,885 帧的累计 GPU 时间从约 400.7 ms 增至 833.5 ms，同时原生整帧间隔约 16.6–18.8 ms，且这些帧未新建管线。首轮据此记录计时归属 / 同步待查，没有把累计值当作真实单帧墙钟或宣布 M4 算力不足。首轮结束后停止运行并报告；后续有界诊断见下，始终保留安全停和原阈值。

首轮采用的上游 `skills/nvn-wire/SKILL.md` 要求阅读 `references/s2arm_lessons.md`，其中明确“GPU 卡死一次即停下报告”。首轮据此结束游戏并报告；随后用户明确要求继续，恢复有界诊断，仍保留安全停。

### 继续诊断：GPU 反馈超出宿主时间区间

`oot-mach-6` 加入仅存在于独立引擎副本的有界逐提交诊断，226.52 秒再次安全退出。第 12,323 帧的一笔反馈为：CPU 提交前采样 `781673.298016000`、GPU 起始 `781670.850820500`、GPU 结束 `781673.311693000`、完成回调 `781673.311843083` 秒。GPU 起始早于提交约 **2,447.20 ms**；反馈跨度 **2,460.87 ms**，而整个提交到回调仅 **13.827 ms**。这条数据足以说明该笔 GPU 时间不能直接用于超时判定，不能解释为真实运行了 2.46 秒。

[Apple 的反馈契约](https://developer.apple.com/documentation/metal/mtl4commitfeedback/gpustarttime) 将起始时间定义为已提交命令缓冲开始执行的宿主时间。独立 Metal 4 小程序分别做了 36 次空命令 / 拷贝和 64 次清除 / load / 拷贝 / 空命令，覆盖缓冲复用、分配器跨段使用及编码中 CPU 延迟；均未复现超出时间区间。**底层异常来源尚未定位，不能声称 Metal 驱动或命令分配器已根修。** 原始反馈见 `oot-mach-6/gpu-time.csv` 和 `measured-summary.json`；两个独立探针在 `resume-gpu/`。

修复的是保护判定信任无效反馈的问题：提交之前采样同一宿主时钟，回调立即采样；只接受位于该区间内的有限、正序 GPU 时间。不合法时把整个宿主区间计入安全预算，它包含排队和回调延迟，是实际 GPU 执行时间的保守上限；该帧的 GPU 耗时 / span 返回未知，不把 CPU 时间充作 GPU 性能指标。宿主区间本身也不合法则直接触发保护。1,000 ms 阈值及 Metal 错误停机路径不变，未加游戏特例、关闭保护或提高阈值。

`tests/s2arm_gpu_timing_test.py` 提取准备后引擎的实际聚合 / 停机函数，重放上述反馈以及合法超时、同帧累计超时、无效反馈但宿主超时、NaN / Inf、环槽复用等 **22 项检查**。原逻辑因上述样本误停而红，修复后通过，回退原逻辑负对照仍红；不向 GPU 提交故意挂死负载。编译通过，Metal 3 / 4 普通及压力四组 56 帧合成视频重新通过。新补丁从固定上游重放，**21 份文件哈希**与实测副本一致；临时逐提交诊断已移除。证据位于 `resume-gpu/timing-*.log`、`timing-replay.json`、`video-regression/`。

修复后的 `oot-mach-7` 完成最长 900 秒的实际游戏复测，证据为该轮 `process.json`、`measured-summary.json`、输入记录、录像及截图。原保护没有关闭，本轮无安全停或 Metal 错误停机。首次私有移动脚本错误复用了报文序号，被接收器拒绝并断开；修正测试脚本后重新操作成功，该次拒绝不算游戏兼容失败。

### 可操作场景与帧间隔

室内回看窗口为原生帧 30,000–32,400，共 2,401 帧 / 52.242 秒，平均 **45.96 FPS**，间隔 p50 / p95 / p99 为 **19.399 / 24.366 / 35.159 ms**，5 次超过 100 ms，最长 **1,920.845 ms**。这是事后选定并明确标注的描述性窗口，不是预设性能验收。

进入森林并确认 HUD 后，预先记录 120 秒观察窗口；实际从第 36,355 帧后到第 41,962 帧，5,607 个间隔共 121.380 秒，平均 **46.19 FPS**，p50 / p95 / p99 为 **20.091 / 24.733 / 30.924 ms**，6 次超过 100 ms，最长 **1,428.992 ms**。期间有移动、爬梯及静止，属于首次访问的短时混合场景；游戏时间相对墙钟速度未独立核对，也不满足正式验收的重复 / 长时要求。

第七轮峰值游戏物理占用 **9.490 GiB**；最长源帧间隔 **13.438 秒**，整轮源间隔超过 100 ms 共 119 次，包含加载与首遇编译。音频容量等待 135,340 次，未发生 bridge 丢块，但背压与间断仍不能证明低延迟或音画同步。需要继续研究持久 shader 缓存 / 预热、冷加载停顿及音频排队；本轮修复不构成这些问题的性能改进对照。

另有尚未解决的上游告警：纹理类型不匹配时读零纹理、未实现音频输入服务、可变着色率退到全速率；runtime-only 根还缺少完整 c1 / PSO 预热资料。没有原机逐帧对照，不能凭出现画面认定所有渲染正确。

## 1402 的真实串流、缓存复用与资源压力

第一轮 `pad1402-resume` 使用公开启动器的全新会话缓存，在确认加载森林后触发 SSD 3 GiB 余量保护。游戏和服务正常退出，空闲空间随后回升。该轮只记录了游戏物理占用，不能追溯确定全部瞬时空间消耗；本机 RomFS 工作副本使用 APFS 克隆，`du` 目录大小不能直接解释为可回收的重复占用。

第二轮 `pad1402-warm` 保持相同引擎、游戏根、测试存档及保护阈值，通过**私有启动包装**把 `oot-mach-7` 的 2,416 个 shader 文件复制到新会话。源 / 目标 SHA-256 全部一致，上游 chain 和 translator 指纹继续校验；未复制 PSO 预热资料，未改变公开启动器。最终 859 个 shader 被复用、42 个新翻译成功。这是同构建缓存可用性的证据；两轮时长、进入场景及背景负载不同，不能据此宣称性能提升比例。持久缓存的版本键、失效、并发写入及原子发布仍需实现。

实际链路为 S2Arm 无窗口呈现 → IOSurface / Mach worker → VideoToolbox → Rust GameStream → 1402 Moonlight。协商 1280×720、H.264、30 FPS、5 Mbps；客户端日志确认使用 `c2.mtk.avc.decoder`，启动 48 kHz 双声道 AudioTrack 并收到首个音频包。它证明网络媒体链路建立，不证明音画同步或客户端实际显示帧率。实际截图包括森林 HUD / 小地图、林克移动及视角变化；`input.tsv` 记录 A 按放、左 / 右摇杆轴值及最后全零。森林存档由先前独立原生会话生成，复制到新测试玩家后读回，原测试源存档没有作为写入目标。

Pad 操作由 ADB 注入屏幕触点，再经既有虚拟手柄发送；本轮没有安装或修改 APK，也不代表人体持握或实体手柄验收。

进入森林后预设 120 秒观察，原生第 4,927 帧后至第 11,720 帧共 6,793 个间隔 / 120.045591 秒：平均 **56.59 FPS**，p50 / p95 / p99 **16.917 / 20.597 / 26.225 ms**，9 次超过 100 ms，最长 **1,376.720 ms**。开始有触屏移动 / 转视角，随后主要静止；游戏时间相对墙钟未验证，不能与前一轮不同场景的 46.19 FPS 直接比较，也不能称为稳定 30 FPS。

本轮约每秒采集各自的 physical footprint，338 个样本中峰值为：

| 进程 / 系统 | 实测 |
| --- | --- |
| 游戏 | 9,363.78 MiB，约 **9.144 GiB** |
| Rust GameStream 服务 | **8.56 MiB** |
| Mach / 编码 worker | **10.09 MiB** |
| 系统 swap | 起始 **4.169 GiB**，峰值 **8.792 GiB** |
| SSD 最低余量 | **9.115 GiB**，未触发 3 GiB 保护 |

共享内存归属不能直接相加。后台远程桌面进程的一次点采约 4.78 GiB，另有其他开发进程，本轮没有结束这些应用。观察更支持先研究游戏资源 / 缓存和整体内存压力，未发现 Rust 服务在这次短测中增长到 GiB 级的证据；不是通用内存泄漏排除或并发容量结论。

客户端返回游戏库后，服务以控制 ping 5 秒超时收局。在最后一个运行中快照（第 14,100 帧）`failed=0`，收局总计 `failed=4`；该计数包含编码 / 传递失败，现有记录没有逐项原因，不能全部归为 VideoToolbox 失败，也不能抹去。音频在控制流停止后记录 bridge error 54 / 39，累计 `bridge_other=33`、`bridge_full=0`，所有 55,452 个 PCM 块仍已释放。退出时视频在途为 0、游戏返回 0，无 GPU 安全停。需继续改善关停顺序与诊断精度。

原始证据在 `pad1402-resume/`、`pad1402-warm/`，包括服务日志、按进程内存、缓存哈希、输入、客户端解码日志、截图、`gameplay-window.json`、`measured-summary.json` 和恢复校验。截图及资源留在忽略目录，不随报告分发。

## 结论与限制

证据支持“固定 S2Arm 后端已接入，用户提供的 OoT 在原生离屏及 Pad 串流中可进入实际游戏、触屏操作并读回测试存档”。**不支持“已完整兼容 OoT / 所有 NS2 游戏”或“稳定 30 FPS”的结论。** 本任务交付基础接入和单款短测；持续游玩、游戏时序、端到端延迟、音画同步、能耗、内存收益及并发容量均未验收。

S2Arm 游戏加载、具体 NVN2 / shader 兼容仍由标题及版本决定。待验证：更多场景 / 实体手柄、重复保存后重启、异常退出恢复、无显示器 / 锁屏、音画同步和长期串流。按需编译存在停顿，音频背压也不能证明低延迟。下一步优先落地带版本校验的持久 shader 缓存，分别测量冷 / 热启动、固定路线与游戏速度，再定位内存、音频排队及关停尾部失败；跟踪于 NXB-128。

上游 Metal 3 性能计数器回归失败原因尚未定位；目前只证明换回原始呈现对象也能复现，不能推断其他机器或任意图形路径都没有问题。
