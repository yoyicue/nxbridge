# 性能与验收

所有门槛都是首版工程目标，不是已达成绩。参考方案、测试工具正常运行、菜单帧率、视频流重复帧都不能作为游戏达标证据。

## 分开测量三条链路

| 链路 | 指标 | 证据要求 |
| --- | --- | --- |
| 游戏本机 | 实际游戏 present / 离屏完成帧的平均 FPS、帧间隔 p50/p95/p99、最长卡顿、game-time / real-time | nxnative 原始帧记录与游戏时序日志；离屏迁移前后定义等价计数边界，排除编码重复帧 |
| 媒体 | 编码 / 解码耗时、接收及呈现 FPS、网络丢包 / 丢帧、排队长度 | Host 和客户端独立统计，解释各计数器口径 |
| 操作 | input-to-photon p50/p95，接收至游戏采样时间，断线释放 | 实际输入与屏幕变化的外部观测，辅以同机阶段时间戳 |

游戏 30 FPS 与串流 60 FPS 可以同时存在，后者可能传输重复画面。不能以 60 FPS 视频计数声称游戏 60 FPS。

## 首轮参数与目标

- 游戏目标 30 FPS；先固定图形设置和同一存档，不在采样期间自动调整画质。
- 初始串流：1280×720、60 FPS、H.264、12 Mbps、SDR；这是实验起点，不是最佳参数结论。对照 30 FPS 串流时分别报告操作延迟。
- Host 尽量有线接入；客户端使用质量良好的 5 GHz Wi‑Fi。记录实际链路，不以标称带宽代替测量。
- 每个游戏样本平均 FPS ≥29.5；帧间隔 p95 ≤40 ms、p99 ≤66.7 ms。超过 100 ms 的停顿单独列出，不因平均值达标忽略。
- 目标 input-to-photon p50 ≤80 ms、p95 ≤120 ms。该目标包含游戏、传输、显示与输入环节，不是网络 RTT。
- 媒体丢帧比例初始目标 <1%，须明确分母与丢帧类型；丢包不能直接等同于画面丢帧。
- 稳定性：30 分钟连续运行不崩溃；20 次受控断线 / 重连没有卡住按键和串会话；网络恢复后的可控恢复目标 ≤5 秒，限于保留会话的宽限期内。
- 冷启动时间、shader 编译卡顿、首次入场记录为独立结果；不能将它们全部排除后宣称整场体验稳定。

最终门槛可由真实体验调整，但必须先记录理由和新版本，不能在看到失败数据后悄悄改口径。

## 采样规程

1. 记录 OS / Xcode、硬件、上游提交、游戏版本、图形设置、资源 / 存档版本、显示刷新率、编码参数、网络条件。
2. 同一份测试存档复制到实验专用玩家档案；真实玩家存档不用于自动跑路线。
3. 分别选择神庙和户外路线。预热与采样窗口预先定义，至少各 10 分钟，重复 3 次；首次编译另外测。
4. 比较本机、Sunshine 基线与 Rust 原生串流，明确帧源；窗口过渡后端仅在已实现时加入。并发比较 1 / 2 / 3 路，每位玩家都记录数据，使用同时发生的样本。
5. 正式采样期间不截屏、不运行 root / 抓帧等高干扰探针。需要光学延迟测量时标记独立实验。
6. 每次操作先确认 CPU / GPU / 网络背景负载及主机内存压力。不要将不可复现的后台清理收益当作默认配置性能。
7. 原始数据写入仓库外或 `artifacts/`。可提交去敏后的摘要、相对引用和内容哈希。

## 延迟的正确口径

不同设备的单调时钟没有共同起点。不能直接相减 Pad 输入时间和 Mac 收到时间，除非使用已验证的校时方案并给出误差界。

同机时间可以拆解 Host 的输入接收、转交和游戏采样。最终 input-to-photon 用高帧率摄影或其他经过验证的外部方法记录实际按键 / 触控与目标屏幕变化；记录帧率和测量精度，采样至少 50 次。没有外部测量时标为 unknown，RTT 和 Moonlight 的“解码耗时”不能替代。

## 多实例必须额外通过

- A / B / C 使用不同标记存档，独立保存、退出、重启后仍对应正确玩家。
- A 的输入、声音和图像不出现在 B / C；用可辨认的画面和音频标记测试，不能只确认端口不同。
- 失焦、遮挡、最小化、锁屏、显示器断开分别记录；未支持的生命周期要限制或提示，不能继续显示“运行正常”。
- 断开 A、杀掉 A 的实验 worker、重启 Host 后，B / C 的存档与控制权保持正确；故障注入只在专用测试会话进行。
- 同一玩家重复开同一游戏必须拒绝第二个写者；重连不创建第二个实例。
- 所有实例分别通过性能门槛，并发容量才可登记为该数量；不以总帧率 90 判断三人各 30 FPS。

## 原生 Rust 服务端与离屏输出

- 协议原型先用 Mac 生成的测试帧 / PCM 连接真实 Moonlight，记录版本、配对 / 证书、实际协商、硬件编解码、输入事件与断线恢复；测试图像不作为 BOTW 成绩。
- 原生真实游戏样本明确记录 NXBridge 媒体后端和运行时帧源。验收过程中不依赖 Sunshine、NX2Apple GUI、屏幕采集或隐藏游戏窗口来提供媒体。
- 验证 GPU 完成后才消费帧、编码器释放后才复用，队列有上限；用原始序号与时间戳确认音画同步、游戏速度和关键帧恢复。慢消费不能导致缓冲无限增长或错误复用。
- 不同设备的时钟口径仍遵循前述要求。主机阶段时间不能替代 input-to-photon，Rust 重写不能替代 A/B 数据。
- 内存分别记录游戏、Host、媒体 worker 的 physical footprint、帧池 / 队列深度、GPU 分配、系统压力与 swap；共享内存统计不直接相加。比较冷启动、预热与稳定运行，不只截取最低占用。

主机状态按以下矩阵独立登记，初始均为 unknown；无窗口是首个原生版本的必达条件，其余项以实测记录支持范围：

| 条件 | 需要证明的行为 |
| --- | --- |
| 已登录、无游戏窗口 | 直接纹理 / PCM 输出，游戏帧率、速度、声音和输入正常 |
| 不接物理显示器 | 分别测启动时无显示器与运行中拔插；记录虚拟显示设备和 WindowServer 依赖 |
| 锁屏 | 帧与音频继续推进、控制与重连行为明确；不以保持网络连接代替健康状态 |
| 开机未登录 / 用户退出登录 | 独立服务启动与资源访问实验；不得从 LaunchAgent 或无显示器结果推导成功 |

Sunshine 对照与原生链路使用同一构建 / 场景 / 编码参数，无法保持相同时注明差异。只有真实原生链路达标才可登记正式后端；后续容量验证使用已确认支持的主机状态。

## 无效与失败数据

OOM / 崩溃是失败结果，进程结束后采不到新帧是无效 FPS 样本，不是游戏 0 FPS。菜单、加载动画和户外场景分开。记录无效原因和原始输出；不删除不利数据、不选择性展示最快一次。

使用 [实验模板](../templates/experiment.json)。缺失数据用 null；result=not_run / invalid / fail / pass 分别表达未测、样本无效、未达标、通过。摘要应指明它实际证明了哪一阶段。
